# 05. CI가 구 Alembic 리비전을 검사해 마이그레이션마다 깨짐

- **프로젝트**: kitae1645/nara-bid-predictor
- **원본**: PR #158 (머지 2026-09-25)
- **스택**: GitHub Actions, PostgreSQL 17.10, Alembic, Docker Compose(임시 CI 스택), pytest
- **분류**: CI / 스키마 이력
- **CS 접점**: 스키마 마이그레이션 이력은 선형 구조이고, 테스트가 그 특정 노드를 하드코딩하면 이력이 자랄 때마다 깨진다. 불변식은 "head가 하나"이지 "리비전 X"가 아니다.

## 한 줄 요약

CI의 두 임시 Compose 스택이 오래된 Alembic 리비전과 오래된 PostgreSQL 클라이언트를 검사하고 있어서, 마이그레이션을 추가할 때마다 CI가 깨졌다. 클라이언트를 서버 이미지와 같은 17.10으로 고정하고, 검사 대상을 `migration graph의 단일 head`로 바꿨다.

## 증상

- 마이그레이션을 추가하면 CI 계약 테스트가 실패. 코드 문제가 아니라 "기대 리비전 문자열 불일치".
- 실제 마이그레이션은 정상 적용되는데 CI만 빨간불 → 팀이 CI를 신뢰하지 않게 되는 전형적인 상태.
- PostgreSQL 클라이언트 버전도 서버 이미지와 어긋나 있었습니다(패키지 인덱스 기준 불일치).

## 조사

1. 실패한 assertion이 하드코딩된 리비전 문자열(`20260802_0025` 등)을 비교하고 있음을 확인.
2. Alembic은 리비전을 **그래프**로 관리합니다. 정상 상태의 정의는 "head가 정확히 하나"이며, 특정 리비전이 아니라 이 성질이 검사 대상이어야 합니다.
3. PGDG 인덱스에서 실제 배포 가능한 패키지(`17.10-1.pgdg24.04+1`)를 확인하고 서버 이미지 태그와 맞췄습니다.

## 원인

두 개의 독립적인 드리프트:

1. **리비전 드리프트**: 테스트가 스키마 이력의 특정 지점을 상수로 갖고 있었음. 이력이 늘어나면 반드시 깨지는 구조.
2. **클라이언트/서버 버전 드리프트**: CI가 설치하는 psql 클라이언트와 테스트용 PostgreSQL 서버 이미지의 메이저/마이너가 달라, 버전 의존 동작(예: 덤프 옵션)이 환경마다 다르게 동작할 수 있었음.

## 해결

```diff
- CI: apt로 임의 버전의 postgresql-client 설치
+ CI: 서버 이미지와 같은 17.10 패키지로 고정 (17.10-1.pgdg24.04+1)

- assert "alembic_version == '20260802_0025'"
+ assert migration graph의 head가 정확히 1개이고, 그 값이 DB의 alembic_version과 일치
```

- 두 임시 Compose CI 검사 모두 같은 head 질의로 통일.
- 계약 테스트를 3개 추가해 **리비전 드리프트**와 **클라이언트/서버 버전 불일치**를 조기에 잡도록 했습니다.

## 검증

| 확인 | 명령 | 결과 |
|------|------|------|
| 새 계약 테스트 | `pytest` (계약 3종) | 3 passed |
| 프론트엔드 | `pnpm lint` / `format:check` / `typecheck` / `test:web` | 156 passed |
| 빌드·감사 | `pnpm build`, `pnpm audit --audit-level high` | 통과 |
| API 전체 | `pytest` | 2,867 passed, 1 failed, 1 skipped |

실패 1건은 이 변경과 무관한 **macOS LibreSSL의 `-checkhost` 미지원** 건입니다([04번 케이스](04-libressl-openssl-portability.md)). Docker가 실행 중이 아니어서 실제 Compose 기동 검증은 하지 못했고, PR 본문에 그 한계를 명시했습니다.

## 운영 경계

이 변경은 **GitHub Actions의 임시 테스트 스택만** 현재 코드의 migration head와 일치시킵니다. 운영 DB에 마이그레이션을 적용하거나 배포를 승인하지 않습니다. 배포 런북은 운영 후보를 `20260802_0025`로 고정하고 있어서, `20260924_0027`의 운영 적용은 별도 검토·승인이 필요합니다.

이 구분을 PR 본문에 남긴 이유: "CI 그린"이 "운영 DB에 적용해도 된다"로 읽히는 순간 사고가 납니다.

## 재발 방지

- 테스트는 값이 아니라 **성질**을 검사 (head 유일성).
- 클라이언트 버전을 서버 이미지와 함께 한 곳에서 관리하고, 불일치를 계약 테스트로 검출.

## 일반화

- **테스트에 상수를 박을 때는 그것이 불변식인지 물어라.** 리비전 번호는 불변식이 아니고, "head가 하나"가 불변식이다.
- **버전 드리프트는 코드 리뷰로 못 잡는다.** CI가 스스로 검사해야 한다.
- **"CI 통과"의 범위를 문장으로 못 박아라.** 테스트 스택과 운영 환경이 다르면, 그 차이를 PR에 적는 것이 리뷰어를 보호한다.
