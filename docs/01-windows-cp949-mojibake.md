# 01. GitHub Actions 로그에서 Windows 명령 출력이 `?????`로 깨짐

- **프로젝트**: kitae1645/mafia42_test
- **원본**: PR #121 (머지 2026-06-28)
- **스택**: GitHub Actions → SSH → Windows Server 2022 (ko-KR), `schtasks` / `tasklist` / `git`
- **분류**: 문자 인코딩
- **CS 접점**: 프로세스 사이를 오가는 건 텍스트가 아니라 바이트다. 인코딩은 각 경계에서 명시적으로 합의되어야 한다.

## 한 줄 요약

한국어 Windows의 `cmd.exe`가 기본 콘솔 코드페이지 CP949로 뱉은 바이트를 Actions 러너가 UTF-8로 해석해 한글이 전부 `?`가 됐고, 모든 SSH 원격 명령 앞에 `chcp 65001 >nul &`를 붙여 UTF-8로 맞췄다.

## 증상

배포 워크플로의 `Restart prod services`, `Health check` 스텝 로그:

```
?????: ?????? ?? "Mafia42Megaphone"?(?) ?????????.
????? ???  PID ??? ??? ???
```

원래 나와야 하는 출력:

```
정보: 예약된 작업 "Mafia42Megaphone"을(를) 중지했습니다.
이미지 이름                     PID 세션 이름 ...
```

- 배포 자체는 성공했습니다. 깨진 건 **로그 가독성**뿐이라 실패로 잡히지 않았고, 그게 오히려 오래 방치된 이유입니다.
- 같은 워크플로의 `echo DEPLOY_SUCCESS`처럼 ASCII만 있는 출력은 정상이었습니다. 즉 인코딩 문제는 **비ASCII 문자에만** 나타납니다.

## 조사

1. 실패한 런의 스텝 원문을 확인 — 깨진 문자열 패턴이 `?`로 균일하게 치환된 형태. 바이트가 유실된 게 아니라 **디코딩이 틀린** 전형적인 형태입니다.
2. 두 호스트(dev, prod) 모두 한국어 Windows. `chcp`를 직접 SSH로 실행해 기본 코드페이지가 `949`임을 확인.
3. 애플리케이션 로그(파이썬 쪽)는 한글이 정상이었습니다. 파이썬이 쓰는 파일·stdout은 UTF-8로 명시되어 있었고, 깨진 건 **cmd.exe 내장 명령의 콘솔 출력**뿐이었습니다. 이걸로 "애플리케이션 인코딩 문제" 가설을 버렸습니다.

## 원인

SSH 세션은 바이트 스트림입니다. 원격에서 `schtasks`가 내는 메시지는 그 호스트의 콘솔 코드페이지(CP949)로 인코딩되는데, GitHub Actions 러너는 받은 바이트를 UTF-8로 간주해 로그에 씁니다. CP949의 한글 바이트열은 UTF-8에서 유효하지 않으므로 대체 문자(`?`)로 치환됩니다.

즉 문제는 세 계층 중 어느 하나의 버그가 아니라, **경계에 인코딩 합의가 없었던 것**입니다.

## 해결

모든 SSH 원격 명령 앞에 코드페이지 전환을 붙입니다. 5개 스텝 전부.

```diff
- 'cd C:\app && git fetch origin && ...'
+ 'chcp 65001 >nul & cd C:\app && git fetch origin && ...'
```

```diff
- 'schtasks /end /tn "Mafia42Megaphone" 2>nul & timeout /t 3 /nobreak >nul & schtasks /run /tn "Mafia42Megaphone"'
+ 'chcp 65001 >nul & schtasks /end /tn "Mafia42Megaphone" 2>nul & timeout /t 3 /nobreak >nul & schtasks /run /tn "Mafia42Megaphone"'
```

- `>nul`은 "현재 코드페이지: 65001" 안내 문구를 지우기 위한 것. 로그에 노이즈를 남기지 않습니다.
- 시스템 로캘·파일 인코딩·애플리케이션 동작은 건드리지 않습니다. 세션 콘솔의 출력 인코딩만 바뀝니다. 그래서 위험도가 낮고 롤백도 쉽습니다.
- 대안으로 검토한 것: PowerShell 스텝으로 전환(`$OutputEncoding`/`[Console]::OutputEncoding` 설정). 스텝 수가 많고 기존 명령이 cmd 문법(`2>nul`, `&` 연결)이라 채택하지 않았습니다.

## 재발 방지

- 워크플로 헤더에 **왜** 이 접두가 필요한지 주석으로 남김
- `AGENTS.md`에 규칙으로 기록: "SSH 스텝을 추가·수정할 때 `chcp 65001 >nul &` 접두를 절대 빼지 말 것"

문서화가 계약 테스트보다 약한 건 사실입니다. 다음에 이 파일을 다시 만질 일이 있으면 "모든 `ssh ... '...'` 라인에 `chcp 65001`이 포함되어 있는가"를 검사하는 테스트를 추가하는 게 맞습니다.

## 일반화

- **경계마다 인코딩을 명시하라.** 파일, 소켓, 프로세스 파이프, 터미널은 각각 다른 기본값을 가진다. "한글이 깨진다"는 신고는 거의 항상 어느 경계에 합의가 없었다는 뜻이다.
- **깨진 문자 패턴으로 원인을 분류할 수 있다.** `?`/`�`로 균일 치환 → 디코딩 오류. 아예 다른 문자로 바뀜 → 코드페이지 불일치. 바이트 유실 → 잘림.
- **성공한 배포도 관측 불가면 실패다.** 로그가 읽히지 않는 상태를 방치하면 그 다음 장애에서 증거를 잃는다.
