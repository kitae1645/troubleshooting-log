# 03. 동시에 실행한 런처 5개가 업데이터 임시 파일에서 충돌

- **프로젝트**: kitae1645/mafia42_test
- **원본**: PR [#153](https://github.com/kitae1645/mafia42_test/pull/153) (머지 2026-07-30)
- **스택**: Windows 배치 런처(`mafia42_5x.bat`, `mafia42_6x.bat`), PowerShell 5.1, Electron 앱 자동 업데이터
- **분류**: 동시성
- **CS 접점**: check-then-act(TOCTOU) 경쟁, 프로세스 간 상호배제, 크로스 세션 뮤텍스 네임스페이스, fail-closed.

## 한 줄 요약

게임 클라이언트 5개를 동시에 띄우는 런처가 버전 업데이트 구간에서 같은 임시 설치 파일에 동시에 접근해 서로의 파일을 지우고 검증하고 있었다. 업데이트 필요 시 **정확히 하나의 업데이터만** 띄우고, 프로세스 탐색·생성을 `Global\Mafia42UpdaterLauncher` 뮤텍스로 직렬화해 해결했다.

## 증상

- `0.0.22 → 0.0.24` 업데이트 중 런처를 5개 띄우면 unhandled rejection.
- 스택에 `Get-AuthenticodeSignature`가 나오는데, 그 시점에 검사 대상 설치 파일이 이미 없음.
- 업데이트가 필요 없을 때(버전 일치)는 항상 정상. **업데이트 구간에서만** 재현됩니다.

## 조사

1. 실패 지점이 인증서 검증이라는 점에서, 서명 자체 문제인지 파일 접근 문제인지 분리. 최신 릴리스의 설치 파일 SHA-512가 `latest.yml` 값과 일치하고 Authenticode 상태가 `Valid`임을 확인 → 서명·무결성 문제 배제.
2. 런처 5개를 순차 실행하면 재현되지 않음. 동시 실행에서만 재현 → 경쟁 상태로 좁힘.
3. `mafia42-updater\pending` 아래 임시 설치 파일이 업데이터들 사이에서 공유된다는 것을 확인. 한 프로세스가 설치 파일을 교체·삭제하는 동안 다른 프로세스가 그 파일을 검사하고 있었습니다.

## 원인

전형적인 check-then-act입니다.

1. 런처마다 "설치된 버전 vs 공식 `latest.yml`"을 **독립적으로** 확인
2. 다섯 개 모두 "업데이트 필요"로 판정
3. 다섯 개 모두 업데이터를 실행
4. 업데이터들이 같은 `pending` 디렉터리의 임시 설치 파일을 각자 정리·교체
5. 어떤 프로세스가 `Get-AuthenticodeSignature`를 호출하는 순간 다른 프로세스가 파일을 지움 → unhandled rejection

버전 확인과 프로세스 생성 사이에 아무 직렬화가 없었던 것이 근본 원인입니다.

## 해결

```diff
+ 버전 비교 게이트: 설치 버전 == latest.yml 릴리스면 기존처럼 5/6개 인스턴스 기동
+ 업데이트 필요(또는 버전 확인 자체가 불안전)하면 메인 프로세스를 1개만 기동
+ 프로세스 탐색 + 생성을 Global\Mafia42UpdaterLauncher 뮤텍스로 감싼다
+ 뮤텍스 생성 / 프로세스 탐색 / 프로세스 생성 중 하나라도 실패하면 fail-closed (아무것도 띄우지 않음)
+ PowerShell 5.1에서 Invoke-WebRequest.Content가 byte[]로 오는 경우 처리
```

핵심 선택 세 가지:

- **뮤텍스 이름에 `Global\`**: `Local\`은 세션 단위라서, 다른 사용자 세션/서비스에서 띄운 런처가 서로를 못 봅니다. 크로스 세션 보호가 필요했으므로 Global 네임스페이스.
- **fail-closed**: 버전 확인이 실패했을 때 "그냥 띄우기"를 선택하면 다시 경쟁 구간으로 들어갑니다. 불확실하면 아무것도 시작하지 않습니다.
- **정상 경로 보존**: 업데이트가 필요 없을 때의 5/6개 동시 기동은 그대로. 락을 상시 걸면 사용자 경험이 나빠집니다.

## 검증

| 시나리오 | 기대 | 실측 |
|---------|------|------|
| 구버전 설치 상태로 실행 | 업데이터 1개만 | 1개 기동, SHA-512 일치, Authenticode `Valid` |
| 최신 버전 설치 상태 | 5개 메인 프로세스 | 5개, CDP 9222–9226 전부 HTTP 200, 경쟁 에러 없음 |
| 버전 확인 강제 실패 | 추가 메인 프로세스 0개 | 0개, 기존 5개 CDP 포트 정상 |
| 동시에 런처 2회 호출(프로세스 0개 상태) | 메인 프로세스 1개 | `MainProcessCount=1` |
| 프로세스 조회 강제 실패 | fail-closed | 기동 없이 종료 |

회귀 테스트: `pytest tests/test_mafia42_launcher.py -q` → 4 passed. 전체 `-m 'not dom'` 623 passed / 109 deselected.

## 재발 방지

- 런처 두 개(5x/6x) 모두에 대해 회귀 커버리지 추가
- 뮤텍스 획득 실패를 침묵하지 않고 종료 코드로 드러냄 (로그 없이 넘어가면 다음에 같은 조사 반복)

## 일반화

- **공유 자원에 대한 "확인 후 행동"은 원자적이지 않다.** 확인과 행동 사이에 다른 실행 주체가 끼어들 수 있으면, 그 구간 전체를 락으로 감싸거나 행동을 하나로 위임해야 한다.
- **뮤텍스 네임스페이스를 의식하라.** Windows의 `Local\`은 세션, `Global\`은 머신 전체. 서비스·스케줄러·다른 로그온 세션이 섞이면 `Global\`이어야 한다.
- **불확실할 때는 아무것도 하지 않는 쪽이 안전하다.** fail-open은 대개 "그냥 되게 해보자"는 유혹인데, 이 경우엔 그 선택이 곧 재현 조건이었다.
